# LiteCP 0.5 development update

This document records the implemented boundaries and release validation for LiteCP 0.5.1. The build was upgraded on the authorized AlmaLinux 10 VPS after a full configuration/data rollback archive was created.

## Implemented

| Area | Behavior and boundaries |
| --- | --- |
| Migration | Inspect ZIP/TAR/TAR.GZ, select cPanel `public_html` or Plesk `httpdocs`, stage files, then atomically switch an empty site's document root. Optional SQL uses the target database's restricted user and resets the previously empty managed database if import or activation fails. 2 GiB upload / 8 GiB extraction / 100,000 entries; at most three retained stages. |
| File manager | New files, multi-select copy/move/trash, filtering, sorting, dotfiles, and existing upload/download/rename/permissions/ZIP/extract. No overwrite on copy, move or restore. ZIP replacement keeps private recovery copies until extraction succeeds. Partial bulk failures are reported explicitly. |
| Code editor | Self-hosted Ace 1.44.0, syntax highlighting, search/replace, undo/redo, word wrap, expanded view and Ctrl/Cmd-S. Loaded only when needed. No remote CDN or worker. Text-only fallback remains available. |
| Trash | Per-site bin outside the public root, restore to original/alternate path, permanent item deletion and empty-bin. No automatic purge. Source and trash must share a filesystem. |
| Firewall | Managed inbound/outbound TCP/UDP allow/deny rules, IP/CIDR scope, edit/delete and rollback on update failure. Host output rules do not cover routed container/VM traffic. Established replies and installer-managed essential access are preserved. |
| PHP extensions | Reviewed optional packages: BCMath, GMP, IMAP, Intl, SOAP, ZIP, Redis. Native removal refuses dependency breakage. Changes affect every site on that PHP runtime. PHP 7.3 container modules remain image-managed. |
| UI | System/light/dark theme, site file-manager shortcut, paginated recent activity (up to 2,000 retained events), password generate/show controls. Previously discarded activity cannot be recovered. |
| Email | Enable/disable without deleting messages, generated SPF/DKIM/DMARC/MX suggestions, optional Roundcube and OpenDKIM installer. Mailbox users log in to webmail separately from the panel. |
| Malware | On-demand ClamAV under the website UID, no automatic deletion/quarantine, bounded output, optional signature-update timer. No resident `clamd` service is added. |
| WAF | Per-site Off/Detect/Block controls, ModSecurity + OWASP CRS integration and optional installer. Existing Nginx TLS directives are preserved. Begin with Detect and tune before Block. |
| Server | Hostname change, persistent IPv4/IPv6 resolver settings, hostname-confirmed reboot. Fresh base installs set 8.8.8.8 and 8.8.4.4; upgrades preserve existing network configuration. |

## Optional component installation

Install the new panel build first using the base installer. Take an off-server backup before upgrading a production machine. Optional components are not installed by default, to preserve LiteCP's lean baseline:

```bash
bash scripts/install-features.sh mail
bash scripts/install-features.sh antivirus
bash scripts/install-features.sh waf
bash scripts/install-features.sh antispam
```

On a fresh base install, `LITECP_INSTALL_WEBMAIL=1`, `LITECP_INSTALL_ANTIVIRUS=1`, and `LITECP_INSTALL_WAF=1` enable these steps. The base installer can be told to retain provider DNS with `LITECP_CONFIGURE_RESOLVERS=0`; private networks may need this.

The optional installer retains configuration snapshots under `/var/backups/litecp/feature-install-*`. Package installations and multi-component upgrades are **not transactional**; review an error and the snapshot before retrying. It must not be run concurrently with panel administration. AlmaLinux WAF builds require development packages, additional disk space, and memory; build jobs are limited to two.

### Mail deployment checklist

- Install a publicly trusted certificate matching Postfix's `myhostname` first. The webmail installer will not disable certificate verification. Self-signed initial LiteCP certificates are not sufficient for ordinary webmail login.
- If the trusted panel certificate already covers the intended mail name, run `LITECP_MAIL_HOSTNAME=mail.example.com bash scripts/install-features.sh mail` with that exact name. This aligns Postfix/Dovecot TLS without changing the OS hostname or public DNS.
- Roundcube 1.7.3 uses an on-demand PHP 8.3 pool (maximum three children), root-owned application code and a private SQLite database. Public login is `https://MAIL_HOSTNAME:8444/`. Allow TCP 8444 at the VPS provider firewall too.
- Publish the domain-specific DKIM key shown in LiteCP. Merge SPF with other legitimate senders instead of creating a second SPF record. Start DMARC with `p=none`, inspect reports, then consider enforcement.
- Create the `postmaster` mailbox/alias if using the supplied DMARC report address. Configure PTR/reverse DNS with the VPS provider, matching forward DNS. Check outbound TCP 25 availability, reputation and actual external delivery.
- DKIM/SPF/DMARC improve authentication; they cannot guarantee inbox placement. The optional Rspamd feature filters inbound and outbound mail; Sieve rules, calendars and shared mailbox permissions remain outside this focused release.
- Authenticated submission is restricted to the mailbox's own envelope sender; aliases are forwarding-only unless explicitly configured by an administrator.

### Migration boundaries

This is a **website files + one selected SQL dump** importer, not a full cPanel/Plesk server restore. It does not migrate mail, DNS, SSL private keys, panel accounts, source cron jobs, addon sites or server configuration. Encrypted/incremental/nested Plesk backups must be exported to a website archive first. Symlinks, ownership and special devices are not restored. Update application credentials and absolute paths before changing public DNS. Files are staged before an atomic document-root switch; failed SQL imports reset the target database after LiteCP has verified that it was empty.

### WAF and scanning boundaries

The AlmaLinux installer builds a connector against the distribution's Nginx development source and does not replace Nginx. Rebuild the connector after an Nginx ABI update; test `nginx -t` before any restart. Ubuntu uses the distribution's Nginx ModSecurity module. The CRS download is pinned; review and update security releases regularly rather than treating the pin as permanent.

The tested AlmaLinux 10 repositories do not provide `yajl-devel`, required for ModSecurity JSON inspection. Rather than enabling AlmaLinux's long-term-unsupported Devel repository or omitting JSON protection, the installer builds checksum-pinned YAJL 2.1.0 inside `/usr/local/modsecurity`. This follows ModSecurity's [official compilation recipe](https://github.com/owasp-modsecurity/ModSecurity/wiki/Compilation-recipes-for-v3.x). The source is old and should be revisited when ModSecurity changes parser support; it is not exposed as a standalone network service.

WAF blocking can affect checkout, payment callbacks, uploads and WordPress administration. Tune false positives per application before production enforcement. Audit logs are rotated in `/var/log/nginx/litecp-waf-*.log`; restrict access because rule matches can contain sensitive data. Scans can consume significant temporary RAM and skip oversized/encrypted content; clean results are not a security guarantee.

## Validation performed (2026-09-05)

- Expanded Go tests, `go vet ./...`, and `go test -race -count=1 ./...` passed in an isolated AlmaLinux 10 VPS source directory.
- Tests cover archive traversal, skipped links, trash restoration/collisions, bulk-operation preflight, pagination overflow, protected firewall ports, resolver validation, WAF TLS preservation, migration endpoint authentication, package allowlists, and output limits.
- `bash -n` passed for both installers; JavaScript syntax checks passed.
- Local browser QA checked migration/dark theme, advanced file-manager controls, PHP editor/search/replace and password generation/show controls. An Ace stylesheet suppression bug found in browser testing was fixed.
- The AlmaLinux 10 WAF build was exercised first in a disposable container: Nginx configuration passed, all 843 CRS rules loaded, a normal request returned 200, and a SQL-injection probe was blocked with 403. The same rule-load and isolated request checks then passed on the live VPS without enabling WAF for the production website.
- ClamAV 1.4.6 installed with current signatures and its update timer active. An EICAR test file was detected and immediately removed.
- Roundcube 1.7.3, OpenDKIM, and the on-demand PHP 8.3 pool installed on the live VPS. Webmail returned HTTPS 200; SMTP, submission, and IMAP listeners all presented the trusted configured certificate; the private Roundcube database and per-domain DKIM key were readable only by their intended service accounts.
- Rspamd 4.1.5, Valkey 8.0, and Unbound installed on the live AlmaLinux VPS. Postfix passed messages through the loopback-only Rspamd milter, and a test message was scored. The installer now assigns Unbound's local port 5353 the required SELinux DNS label.
- LiteCP 0.5.1, Nginx, MySQL 8.4, Postfix, Dovecot, OpenDKIM, Rspamd, PHP 7.3/7.4/8.1/8.2/8.3/8.4, and the ClamAV update timer were active after upgrade. Existing website, database, mailbox, and mail-domain records were preserved.
- AlmaLinux SELinux was switched from permissive to enforcing after a controlled restart, mail synchronization, spam scan, website, panel, and webmail test produced no new denials. Automatic security updates and Fail2ban mail/SSH jails are active. Resolver changes were exercised and persisted as 8.8.8.8 and 8.8.4.4.
- **Remaining cross-platform/external validation:** a fresh Ubuntu installation; native extension add/remove and live outbound-rule enforcement on both operating systems; authenticated mailbox send/receive after publishing matching MX/SPF/DKIM/DMARC and PTR records. Reboot and hostname changes were intentionally not exercised on the production VPS.
